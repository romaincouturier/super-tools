# Architecture
- Book enrichment uses a persistent per-production queue, a leased three-item worker and snapshot-checked field updates; provider failures pause the queue, because enrichment must preserve manual edits and never replay an unknown inference outcome.
- MCP media previews use short-lived Storage transforms before decoding; crops decode only header-verified images bounded to 1600² pixels, local original fallback requires both small bytes and bounded dimensions, and all image downloads have streamed byte limits and a timeout, because compressed size alone cannot protect Edge memory. No auth, RLS or public access changes are permitted for this path.
- Rental creation paths share an awaited generation/send workflow; reuse originals and sent signatures, preserve active rentals on webhook replay, and record failures, because missing PDFs must never silently block or duplicate contracts.
- Attendance notifications share a read-only trainer resolver (linked ID, unique legacy name, default when unassigned); explicit or ambiguous trainers never fall back to another recipient, because missing links must not silently suppress or misdirect emails.
- Tender digests filter each notice before exclusions; daily source health uses Paris business-day import age, because rejecting one notice must not hide the whole feed.
- Training communities have their own course link, independent of supports/enrollment; learner email links use training-community.ts and internal daily alerts reuse the pending LMS queue, because selecting a community must not change course access or duplicate alerts.
- Physical training access uses a shared resolver (session override, venue link or unique exact legacy address match) and email-safe rendering; daily alerts use the same resolver and a strict seven-day boundary, so legacy sessions inherit real venue instructions without changing session data.
- Qualiopi screen and scheduled audit share a paginated read-only collector; only evidenced questions are auto-answered and missing responses are not missing processes, because partial samples and placeholder zeros must not invent non-conformities.
- Qualiopi focus is stored inside each automatic run's facts and shared by email and UI; unresolved focus members block advancing to the next pair, and affected items retain their own missing evidence and deep links, because a global count cannot identify the dossier to correct.
- Transcript controls use persistent, manually resumed source inventories; repairs require a selected source ID, preserve trashed rows and suppress downstream notifications/generations via stored metadata, because presence alone cannot certify completeness.
- Fireflies refresh always checks the latest 30 meetings without a historical cursor and imports every missing one; historical pagination belongs to inventory controls, because a frozen cutoff hides newly missed meetings from both the button and MCP.
- Attestation rules live in execution-attestation.ts and in a DB trigger (edits draft sent ones, signed frozen, token hashes only), to keep signed content provable.
- Project action assignments use project-assignee.ts in UI, MCP, daily generation and completion checks; profile emails are service-role aliases and unknown/ambiguous values explicitly target creator plus admins, because label-only matching silently routed email assignments to creators.
- Drive meeting discovery scans configured roots and the Meet tree with pagination and Drive-ID deduplication; oversized MP4 recordings extract AAC in bounded, ordered parts stored in transcript metadata, because upload and duration limits must never silently truncate meetings.
- Audit blank manual answers are an append-only evidence journal (`audit_question_evidence`) merged by `_shared/audit-evidence.ts` in UI, MCP and run-qualiopi-audit; evidence older than the shared max age reverts to unconfirmed, because agent and human proofs must stay traceable and the verdict must agree everywhere.
- Rental shipping state (wait/prepare/invalid/done) comes from `_shared/rental-shipping.ts`, shared by the orders screen and daily actions; the internal "ready to ship" email goes once per contract to the `rental_shipping_notify_email` setting, because shipping must follow the contract status without hard-coded recipients.
